# Sequence diagrams — v1.2 design and conformance worklist

**Status: v1.2 implementation candidate; cross-platform release validation is pending.** The separate `type: sequence` grammar compiles lifelines, messages, execution bars, annotated occurrences, fragments, interaction uses, gates, coregions, continuations and same-source inline part decompositions to SVG, PNG and vector PDF. Source order is a deterministic placement tie-break, not a simulated trace. Explicit `layout` rules are mandatory; the renderer expands downstream rows when a constrained coregion needs more space. Contextual LSS selectors apply to visible sequence parts. See the [delivered syntax](language-reference.md#sequence-diagrams), the buildable `examples/sequence-*.laml` sources, and the [clause-by-clause UML 2.5.1 audit](uml-sequence-conformance.md). The outer `sd` interaction frame remains deliberately deferred until after the other diagram types; conditional execution bars at a divergent fragment join fail by explicit product decision. Text and external model semantics are never executed. Do not claim literal coverage of the deferred UML frame or unsupported cross-diagram model relationships.

## Product boundary

LAML produces images, not UML models, execution traces, or XMI. Every source construct must either create visible notation, determine its visible placement, or disambiguate a shorthand needed to draw it. There is no requirement to define invisible classes, operation signatures, or executable guards. A visible label may include type, signature, argument, or guard text without LAML pretending to verify an external program's type system.

One `.laml` source produces one SVG, PNG, or PDF. Referenced source files, when explicitly supplied, do not silently embed another diagram. Geometry is derived from current source and styling; explicit constraints are mandatory and unsatisfiable constraints fail. Existing graph diagrams without a diagram type retain their previous meaning.

`check` validates syntax, references, and by default statically decidable diagram rules. `settings { semantic-check: off }` (on its own line) currently disables the additional numeric loop-bound comparison (`min <= max`), including inside inline decompositions. It does **not** disable prerequisites for drawing such as resolvable lifelines, balanced fragment lifetimes, unambiguous shorthand, or mandatory layout constraints. `build` additionally measures, lays out, and renders, failing rather than drawing an impossible or misleading result. No guard simulation.

## Settled syntax and behavior

The following describes the agreed **design**, not current compiler behavior:

```text
settings {
    type: sequence
}
semantics {
    Client(label="Browser")
    API(label="Orders API")

    request: Client -> API+ : GET /orders
    <-- : 200 OK

    Client ->> API : notify
    Client <- API : synchronous call from API
}
layout {
    Client < API : gap=48
}
```

- Lifelines use existing node-declaration syntax; references to undeclared lifelines are errors **except** that a first standalone `API+`, `API(label="Orders API")+`, or first rightward target `Client -> API+` introduces a lifeline at that event. `+` starts the execution bar. A plain prior `API`/`API(label="Orders API")` declaration draws the participant header at the top **without** starting an execution bar; subsequent `API+` starts only execution. `API!` draws X and ends the lifeline; no later event can reference API. Declaration/first-introduction order determines default left-to-right order.
- Messages use existing relation declarations, including optional relation IDs. `->` is a synchronous call; `<-` is the same kind of call with reversed direction; `->>` is asynchronous and `<<-` is its leftward mirror. An async call and async signal share the visible arrow but may receive an optional explicit kind when a distinction is needed in the source. Dashed replies may name both endpoints or use leading `<--` to refer to the most recent unambiguously open call on the applicable path. A reply is not required to be shown for every call.
- `+`/`-` on lifelines, either standalone or attached to a message endpoint, start/end visible execution bars. An unmatched `-` is an error. A compact `<--` closes the corresponding visible execution if present; an explicit dashed reply without `-` can leave it open, and a dashed reply with `-` closes it. Call tracking exists only to resolve this drawable shorthand; it is not a full runtime or UML model.
- The default dashed reply has an open arrowhead; a filled arrowhead remains expressible. Names are optional for ordinary messages and required only when a specific message or its send/receive position must be addressed (or a shorthand would otherwise be ambiguous). An ID is an authoring anchor, not automatically printed text.
- `alt` may contain short replies inside operands. Outside a fragment, `<--` is legal only when it resolves unambiguously across all applicable branches. `par` must not imply inter-operand chronological order. Edit-induced movement of other elements is permitted.
- `ref "Interaction name"` creates a visible interaction-use frame with a displayed name; it does not resolve another local file merely to draw the frame. Explicit local-file references and lifeline coverage are still to be designed and implemented. No automatic expansion or UML-model import.

Named notes keep content and placement separate: `retryHint: note "Retry once"` in `semantics` and `retryHint over API : gap=16` in `layout`. The ID may be referenced as `note[retryHint]` in `styling`. Every note currently requires exactly one placement over a declared participant or an earlier, unambiguously named message end (`retryHint over request.receive` or `retryHint over request.send`). Message-end placement draws a dashed connection to that endpoint and positions the note to its right. `gap` reserves vertical space before the note's own source-order row; it is not a horizontal offset. Repeated or unknown IDs fail. See `examples/sequence-notes.laml`. Placement over a range of participants is not implemented.

Inline part decomposition lives in the same file: `decompose API "Internals" { ... }` contains one child declaration or message per line in `semantics`; local layout is qualified (`API.Cache < API.DB : gap=36`) in the root `layout` section. The participant head displays `ref Internals`; its child lifelines and messages appear beneath it. No file is loaded. IDs of child lifelines are local to their decomposition: `API.Cache` and `Worker.Cache` are distinct layout references, while LSS `node[Cache]` matches both, `node[API] node[Cache]` matches only API's child, and `node.critical node[Cache]` matches children of classed participants. The space separates ancestor and descendant selectors, as in CSS. This also works for nested messages and other visible children, for example `node[API] relation[query]`; unqualified `relation[query]` applies to all matching message IDs across decomposition scopes. See `examples/sequence-decomposition.laml`. This is a drawable first slice, **not yet full UML inline part decomposition**: qualified root layout rules now place nested notes (`API.hint over API.query.receive`) and continuations (`API.condition spans API.Cache,API.DB`), while precise boundary-crossing and strict-ordering semantics remain open. A root combined-fragment frame can already visibly span a same-source inline decomposition; this does not yet validate all UML global-fragment semantics. The outer `sd` frame is deferred by product decision.

Continuations keep their text in `semantics` and placement in `layout`: `condition: continuation "Wait"` followed by `condition spans A,B : gap=16`. The rounded symbol can cover one or several lifelines, and `continuation[condition]` styles it; see `examples/sequence-continuation.laml`. A curly-braced state invariant can be attached to a named occurrence with `at[request.receive] : invariant="ready"`. These are visual annotations, not evaluated state checks.

Coregions group **named occurrence endpoints**, not whole messages: after `first: A -> API` and `second: B -> API`, write `coregion API {` then `first.receive` and `second.receive` on separate lines, then `}` in `semantics`. In `layout`, `second.receive above first.receive` can reverse their *visible* height without claiming a temporal order. That may produce sloped message lines. Both references must lie on the named participant, and vertical rules must be acyclic and stay within one coregion. See `examples/sequence-coregion.laml`. The current solver may expand occurrence heights to keep all messages horizontal or downward (UML §17.4.4.1). `second.receive above first.receive : gap=140` enforces a minimum vertical separation within one coregion; a mandatory gap expands later rows, execution bars, enclosing fragment frames and the canvas, keeping later lifeline occurrences below the reordered endpoints. General collision avoidance across annotation text and unrelated symbols remains open. Style the brackets with `coregion` or `coregion[API]`, or contextually via `node.critical coregion` if the participant has `classes=critical`.

`ignore "cancel, update" { ... }`, `consider "create" { ... }`, and `assert consider "create" { ... }` show a message-name list in braces inside the fragment descriptor, as UML §17.6.4.4 requires; names are display text, not dynamically evaluated. Fragments can have optional IDs for per-frame styling and coverage: `checkout: alt "yes" { ... }` plus `checkout covers API,Worker` in `layout` draws a frame limited to those lifelines. Coverage must list every lifeline between its leftmost and rightmost members; it rejects events on outside lifelines and frames that would overlap neighboring heads. `fragment[alt]` still styles every alt, while `fragment[checkout]` wins for that named frame. An instance ID cannot reuse a fragment-operator name.

A named bar boundary may be used in general ordering as `execution(API,work).start` or `.finish`; this is an explicit occurrence reference, not a placement constraint. Individual executions may be named locally to their participant: `work: API+ : "Validate order"`, followed by `work: API-` (or plain `API-` for the last open bar). The participant ID is still `API`; `work` distinguishes only that bar. LSS `activation[API]` styles all API bars, while `node[API] activation[work]` targets one. Unnamed bars retain existing `API+`/`API-` behavior; see `examples/sequence-executions.laml`. Vertical placement constraints for individual bar boundaries are not implemented yet.

## Conformance matrix (notation to be specified and tested)

| ID | Visible UML coverage | Syntax needed | Validation / layout acceptance |
|---|---|---|---|
| S01 | Interaction frame, title, lifeline heads, optional visible type/selector/self | `API(selector="u"; type="Service")` and `self` display UML-style heads; outer `sd` frame deferred | Names and headers fit; lifelines ordered and distinct |
| S02 | Sync call, async call/signal, reply; leftward, rightward, self; open/filled arrowheads | Arrow forms; `reply(arrow=filled): A <-- B` or named `<--` for filled reply. Async call/signal have the same visible arrow, so no invisible distinction is stored | Message segments must be horizontal or downward; head style is visible; no invented return required |
| S03 | Complete, found, lost messages; messages through frame boundaries/gates | `? -> API`, `API -> ?`, and named `gate[id]` in `ref` blocks supported | Unknown end is a dot; named gate meets the frame boundary; full UML gate semantics still open |
| S04 | Creation and destruction | `spawn(kind=create): Client -> API+` explicitly draws a dashed open creation message; plain first `Client -> API+` retains the established sync-call shorthand. `API!` or `Client -> API! : delete` draws X (the latter has a terminating deletion path). `alt` operands can contain local birth and death of a previously unknown ID | Lifeline starts at first introduction, ends with X; no later drawn occurrence. Each operand-local birth must end in its own operand; repeated births of one ID across alternative operands draw independent segments |
| S05 | Execution specifications, nesting, action/behavior variants as visible | `API+`/`API-` stack bars; `work: API+ : "Validate"` gives one bar a local ID and a wide label; `work: API-` can close it explicitly | `activation[API]` affects all API bars; `node[API] activation[work]` targets one. | S06 | Combined fragments: alt, opt, loop, break, par, strict, seq, critical, neg, assert, ignore, consider | Nested blocks, guard text, loop bounds, pentagon descriptors and optional instance IDs (`checkout: alt "yes" {`) supported; operator-specific semantics incomplete | `checkout covers API,Worker` in `layout` constrains frame lifeline coverage; large operand labels expand frame and canvas; divergent open execution bars fail at the join by decision |
| S07 | Interaction use (ref), actual/formal gates, visible arguments/return labels | One-line `ref "Name"` or named block `lookup: ref "Name" { ... }` with named `gate[id]` endpoints and a pentagon `ref` descriptor supported; the quoted ref label can contain UML-style arguments/return text literally; external formal/actual mapping is not inferred without a target model | `lookup covers API` limits a named ref frame to its lifeline; gate endpoints meet that frame's boundary; no target file is loaded |

| S09 | General ordering, time and duration observation/constraint | Named `.send`/`.receive` anchors; four distinct time/duration attributes; `order[first.receive,second.send]` draws a directed ordering link | Anchored text/bracket/order link; local ordering cycles checked; full normative notation and other anchor types not yet supported |

Frieder explicitly deferred the outer `sd` interaction frame until after the other diagram types are implemented. It is **out of scope for v1.2**, despite being normative UML notation. Do not claim literal coverage of every drawable UML 2.5.1 shape in v1.2; document this deliberate exception. Fragment and `ref` frames now have pentagon descriptors. The outer interaction frame remains deferred until after the other diagram types. Message arrowheads now share the styled stroke color; named self-message send and receive anchors have different vertical positions. Notes are a LAML authoring convenience and must not be conflated with Table 17.1's core sequence nodes. The audit is in progress; these are verified clauses, not a complete coverage claim. §17.4.4.1 specifies a delete message ending at an X, now drawn via `A -> B!`; §17.3.4.1 permits visible lifeline selector/type, now available as quoted `selector`/`type` attributes. §17.2.4.4 permits an Action symbol linked to a reception occurrence: `at[request.receive] : action="Read"` now draws a box and a link. §17.6.4.9 permits `loop(0,0)`; zero maximum is no longer incorrectly rejected. Figure 17.5 places time observations with leader lines and shows duration observations on messages; the renderer now distinguishes equal-height message-duration leaders from vertical two-occurrence brackets. Figure 17.14 includes creation and destruction within an `alt` operand: a participant may now be introduced and destroyed inside the same operand; open lifetimes at the operand boundary fail. Repeated births of the same ID in alternative operands draw separate heads and lifeline segments with shared styling. A pre-existing lifeline may also be destroyed in every alternative; the renderer draws its lifetime separately in each operand after the first branch. Inconsistent branch outcomes fail. Frames reserve horizontal room for their guards, so participant lifelines do not cross guard text.

Rows are a worklist, **not evidence that all UML 2.5.1 cases have been enumerated**. For each row, cross-reference normative clauses and figures, record both positive and negative source examples, and inspect SVG plus PNG/PDF. Features without a notation in UML must not be invented and presented as normative. Note that optional shorthand is LAML syntax, not a claim about UML's own textual syntax.

## Implementation order and architecture

1. Preserve the current graph-document parser unchanged for files without `type: sequence`; add a type discriminator and sequence-specific AST/parser. Nested fragment blocks require a real context stack rather than the current single `Section::Semantics` state (`src/parser/mod.rs`). Keep Rust files under 500 lines (`AGENTS.md`).
2. Represent only drawable information: lifeline headers, messages with graphical send/receive anchors, execution bars, fragment frames and operands, annotations, and refs. A dependency graph of visible placements is allowed as an implementation detail; no invisible UML class model.
3. Validate names, references, shorthand resolution by branch, drawable ordering, and activation closure. Define exactly which optional checks the semantic-check setting disables. Avoid rejecting valid images merely because they omit a return or visible execution. The current fragment parser clones the call context per branch and refuses shorthand after divergent calls, but rejects divergent visible executions at a join. **Decision:** At a fragment join, every operand must leave the same open execution bars, from the same opening occurrences. Divergence is an error rather than a conditional continuation or an invented implicit close. Bars already open before the fragment may continue if every operand preserves them; bars may end if every operand closes them. A bar opened within an operand must be closed there. This deliberately excludes diagrams with conditional post-fragment executions; do not claim literal coverage of those UML cases.
4. Measure text and solve lane widths/ordering; place per-lifeline occurrences, message endpoints, nested frames, and annotations. Separate the source-order tie-break used for deterministic rendering from the order claimed by the UML diagram. Support sloped messages when needed; do not force every message to one global row.
5. Render a single geometric result through the existing SVG/PNG/PDF export path; extend LSS selectors only for visible sequence objects. A basic independent sequence renderer now shares export conversion and atomic CLI writing, but not graph routing. Tests added for SVG primitives and PNG/PDF conversion; preserve previous graph results.
6. Complete the clause-by-clause normative conformance audit before describing sequence support as complete or releasing v1.2.

## Syntax still to finalize before coding the corresponding feature

- Async call and signal have the same visible arrow per UML §17.4.4.1; LAML does not need an invisible call/signal distinction to draw them. Filled reply heads are implemented with `reply(arrow=filled): A <-- B` or `reply(arrow=filled): <--`.
- An explicit reply with both endpoints plus a participant-local named execution close already disambiguates what is drawn; an additional hidden call-instance reference is not required for the image contract.
- Standalone `+`/`-` positioning relative to messages and explicit reply variants. Local execution IDs and labeled wide bars are implemented, while the precise `layout` constraints addressing individual bars remain to be designed.
- Formal grammar of non-loop fragment attributes, operator-specific validation, and lifeline coverage of frames. Structured loop bounds and optional text guard are implemented.
- Complete drawable boundary-crossing cases. No invisible formal/actual gate mapping is required when the referenced target is not loaded. Leftward creation and deletion message targets can use `Worker+ <- Client` / `Worker! <- Client`; put `Worker < Client` in `layout` if the target must be visually left. Explicit `kind=create` and `arrow=filled` now cover the visible message distinctions; curly-braced state invariants and continuation symbols are implemented, while part decomposition remains open.
- Remaining LSS size properties and contextual styling beyond participant parts, annotations, gates and order links. Coregion `above` accepts `gap=number` and expands downstream rows and frames; collisions with unrelated text/symbols still need scrutiny.

These are language-design details, not permission to omit the corresponding visible UML constructs from v1.2.
